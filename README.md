## ГЛАВНОЕ: paper — это не настоящие сделки

В самом начале каждого запуска бот печатает свой режим:

```
   Режим: 📄 PAPER — сделки НЕ отправляются на биржу, всё считается локально
   ⚠️  Это бумажный режим. Реальных ордеров на MEXC не будет — все «сделки» только в этом окне.
```

| Режим | Что происходит | Реальные деньги |
|-------|----------------|-----------------|
| `paper` | Бот считает сделки в памяти. На бирже **ничего** нет. | Нет |
| `demo` | Ордера идут на тестовую площадку MEXC | Нет |
| `live` | Ордера идут на реальную биржу | **Да** |

Проценты профита в `paper` — это расчёт «если бы сделка состоялась».
Никаких ордеров на MEXC в этом режиме не создаётся.

### Как включить реальную торговлю

В файле `.env`:
```
MODE=live
CONFIRM_LIVE=YES
```

Без `CONFIRM_LIVE=YES` бот не запустится в live — защита от случайного
включения настоящих денег одной строкой.

## Настройка — файл `.env`

Все параметры вынесены в `.env`, код править не нужно.

| Параметр | Что делает |
|---|---|
| `MODE` | `paper` / `demo` / `live` |
| `MARKET_TYPE` | `swap` (фьючерсы) или `spot` |
| `MARGIN_MODE` | `isolated` / `cross` |
| `SYMBOLS` | `AUTO` — бот сам отберёт пары по обороту. Или список через запятую |
| `MAX_SYMBOLS` | сколько пар сканировать за проход (AUTO) |
| `MIN_SYMBOL_VOLUME` | порог оборота 24ч для AUTO, USDT |
| `SYMBOL_REFRESH_MINUTES` | как часто пересобирать список (AUTO) |
| `TIMEFRAME` | таймфрейм свечей. Меньше — больше сигналов |
| `POSITION_VALUE` | объём одной сделки в USDT. `0` = считать от `MAX_POSITION_PCT` |
| `MAX_OPEN_POSITIONS` | сколько позиций одновременно |
| `LEVERAGE` | плечо |
| `MAX_LEVERAGE` | потолок для `LEVERAGE`. Должен быть **не меньше** `LEVERAGE`, иначе бот не стартует |
| `RISK_PER_TRADE_PCT` | сколько % депозита теряем, если сработает стоп. Считается **до** `POSITION_VALUE` и может урезать сделку — см. ниже |
| `SYMBOLS_EXCLUDE` | пары, которые нельзя торговать, через запятую (без суффикса `:USDT`) |
| `SYMBOLS_EXCLUDE_SUFFIX` | отсечь по суффиксу, например `STOCK` — убирает токенизированные акции |
| `HEARTBEAT_SECONDS` | как часто печать «бот жив», когда сделок нет |
| `EMA_FAST` / `EMA_SLOW` | периоды скользящих средних |
| `RSI_LONG_MIN` / `RSI_LONG_MAX` | полоса RSI для входа в лонг |
| `RSI_SHORT_MIN` / `RSI_SHORT_MAX` | полоса RSI для входа в шорт |
| `STOP_ATR` / `TAKE_ATR` | стоп и цель в ATR (база, поверх неё работают проценты ниже) |
| `TAKE_PROFIT_MIN_PCT` / `TAKE_PROFIT_MAX_PCT` | коридор цели в процентах. По умолчанию `2` и `3` |
| `MAX_STOP_PCT` | потолок ширины стопа в процентах. По умолчанию `4` |
| `MIN_REWARD_RATIO` | минимальное отношение «цель / стоп». По умолчанию `1` |
| `MIN_STOP_PCT` | стопы уже этого процента отбрасываются — съедаются комиссией |

Чем шире полосы RSI — тем больше сигналов и больше сделок.

### `RISK_PER_TRADE_PCT` может тихо урезать сделку

Порядок такой: сначала считается размер «по риску»
(`equity × RISK_PER_TRADE_PCT`), потом он сравнивается с `POSITION_VALUE`,
и берётся **меньший**. На маленьком депозите риск-потолок часто оказывается
ниже `POSITION_VALUE` — и сделка получается в разы меньше заказанной.

Именно это было при `RISK_PER_TRADE_PCT=0.5` и депозите 10.18 USDT: риск
0.051 USDT при стопе 2% разрешал номинал 2.5 USDT, поэтому LINK открывался
на **1.43 USDT** вместо 3, а профит был 0.029 вместо 0.058. Теперь `1%` —
это страховка сверху, а размер задаёт `POSITION_VALUE`.

Если позиция всё же вышла меньше `POSITION_VALUE`, бот прямо пишет причину
в карточке входа:

```
📉 Размер ниже POSITION_VALUE=3.00 USDT: получилось 2.35 — биржа торгует
   целыми контрактами по 1.18 USDT, округление вниз дало меньше
```

Три возможные причины: риск-потолок, целые контракты биржи, либо
`MIN_ORDER_VALUE`. Карточка называет конкретную.

**Типичная ошибка:** ставить `POSITION_VALUE=3` вместе с крошечным
`RISK_PER_TRADE_PCT` и удивляться, что позиции вдвое меньше заказанного.

## Сколько пар на MEXC и почему бот сканирует не все

На MEXC-фьючерсах **1071 пара** в USDT. Проверить все за проход нельзя:
`fetch_ohlcv` — это отдельный HTTP-запрос на каждую пару, то есть 1071
запрос и несколько минут ожидания вместо 15-секундного цикла.

Поэтому в `.env` есть режим `SYMBOLS=AUTO`:

```
MAX_SYMBOLS=20            # сколько пар сканировать за проход
MIN_SYMBOL_VOLUME=5000000 # порог оборота 24ч, USDT
SYMBOL_REFRESH_MINUTES=60 # как часто пересобирать список
```

Бот берёт все тикеры MEXC **одним запросом**, сортирует по обороту,
отбрасывает пары дороже `POSITION_VALUE` и режет до `MAX_SYMBOLS`.
Список обновляется раз в `SYMBOL_REFRESH_MINUTES` — новые листинги
попадают в работу сами.

Цена вопроса: каждый проход = `MAX_SYMBOLS` запросов. Ориентиры:

| `MAX_SYMBOLS` | время прохода | с чем придётся мириться |
|---|---|---|
| 10 | ~5 сек | только крупнейшие пары |
| 20 | ~10 сек | оптимально |
| 40 | ~20 сек | надо поднять `ENTRY_SCAN_SECONDS` до 30+ |
| 100+ | 1 мин+ | проход не успевает, сигналы опаздывают |

Хотите конкретные пары — впишите список, `AUTO` отключится:
```
SYMBOLS=BTC/USDT,DOGE/USDT,WIF/USDT
```

## Главное: paper проверяет настоящие заявки

Раньше бумажный режим **не проверял работу с биржей вообще**. В `open()`
буквально стояло:

```python
if self.paper:
    self._positions[symbol] = Position(...)
    return price          # ← и всё
```

То есть в paper не выполнялись `set_leverage`, `create_order` и, главное,
`_place_protection` — установка стоп-лосса и тейк-профита. Из-за этого
ошибки этих вызовов всплывали только на реальных деньгах: в paper «всё
работало», в live — нет.

Сейчас заявка собирается **одинаково** в обоих режимах и печатается
целиком. Разница ровно одна: в paper сеть не трогается.

```
📤 ВХОД · SUI/USDT:USDT buy 2 контракта · side=buy openType=cross positionType=long leverage=3
📤 ЗАЩИТА СТОП-ЛОСС @1.1681 · SUI/USDT:USDT sell 2 контракта · triggerPrice=1.1681 triggerType=2 orderType=5 executeCycle=2 side=sell reduceOnly=true
📤 ЗАЩИТА ТЕЙК-ПРОФИТ @1.1871 · SUI/USDT:USDT sell 2 контракта · triggerPrice=1.1871 triggerType=1 orderType=5 executeCycle=2 side=sell reduceOnly=true
```

Это ровно тот JSON, который уйдёт на биржу при `MODE=live`. Если MEXC
не примет какое-то поле — в paper будет видно, что бот даже не смог собрать
заявку, а не «всё хорошо, а на деньгах отказ».

Дополнительно в paper теперь **работают стопы и тейки**: позиция
закрывается на бумаге, печатается PnL, баланс меняется. Раньше бумажные
позиции не закрывались никогда, и баланс навсегда оставался равен
`PAPER_BALANCE`.

## Цель сделки: 2-3%

Раньше цель задавалась только через ATR: `TAKE_ATR=3` от среднего
истинного диапазона. На 5-минутных свечах ATR мелкий, и цель выходила
**0.37-1.49%** — меньше процента, комиссия и спред съедали почти весь смысл
сделки. Замерено на реальных данных:

| пара | старая цель | новая цель |
|---|---:|---:|
| XRP | 0.37% | 2.00% |
| SOL | 0.38% | 2.00% |
| DOGE | 0.46% | 2.00% |
| ADA | 0.70% | 2.00% |
| SUI | 0.95% | 2.00% |
| LINK | 1.49% | 2.00% |

Теперь цель считается процентами и удерживается в диапазоне
`TAKE_PROFIT_MIN_PCT`..`TAKE_PROFIT_MAX_PCT` (по умолчанию 2..3). Если
ATR-цель внутри этого диапазона — берётся она, иначе граница.

Стоп расширяется вслед за целью, чтобы отношение «цель / стоп» было не хуже
`MIN_REWARD_RATIO`, но не шире `MAX_STOP_PCT` (4%).

### Честное предупреждение

**2-3% и «торговать почаще» — это противоположные требования.** Чем дальше
цель, тем реже она достигается. При `MIN_REWARD_RATIO=1` (цель = стоп) безубыток
наступает при 50% успешных сделок минус комиссия, то есть фактически нужна
win-rate выше 55-60%. Если хотите больше профита с меньшим числом сделок —
поднимите `MIN_REWARD_RATIO` до 1.5-2.

При `POSITION_VALUE=3` и цели 2.5% профит по сделке — **0.075 USDT**. На
депозите 10.18 USDT это меньше процента за сделку: 20 сделок дают около
1.5 USDT. Реалистично быстрый рост на таком депозите невозможен, это чисто
масштаб.

## Плечо 7x

`LEVERAGE=7`, `MAX_LEVERAGE=15` (последний не может быть меньше `LEVERAGE`,
иначе бот не стартует).

- маржа на позицию: `POSITION_VALUE / LEVERAGE` = `3 / 7` = **0.43 USDT**
- ликвидация примерно на **14.3%** против движения
- стоп ограничен 4% (`MAX_STOP_PCT`), то есть до ликвидации дело не доходит

Опасность не в марже, а в том, что при 7x ошибка в цене входа дороже
обходится: комиссия считается от номинала, а не от маржи.

## Почему бот «останавливался после одного круга»

В live выход из позиции был возложен целиком на стоп-ордера биржи. Их
нельзя было ни надёжно проверить, ни снять, поэтому позиции не закрывались:
слоты кончались, и бот крутился вхолостую, не открывая ничего.

Теперь `broker.manage_exits()` на каждом шаге сверяет текущую цену с
записанными стопом и целью и закрывает позицию обычным ордером, освобождая
слот. Если стоп на бирже сработает раньше и закроет позицию, лишний запрос
вернёт `Position is nonexistent` — это обрабатывается как штатная ситуация.

В лог падает:

```
🎯 Цель достигнута SUI/USDT:USDT LONG 2 контракта: вход 1.174 → 1.201
   (+2.30%) · PnL +0.0640 USDT · слот освобождён, ищу новую сделку
```

### Позиции от прошлых запусков

Стоп и цель живут в памяти бота. Позиции, открытые **предыдущим** запуском,
новый бот не знает — у них нет ни стопа, ни цели, и закрыть их по уровню он
не сможет. На старте бот честно пишет об этом:

```
📂 На бирже уже открыто 5 позиций: AAVE↑, ADA↑, LINK↑, PHA↑, SUI↑
⚠️ У 5 из них бот не знает стоп и цель — они открыты прошлым запуском.
```

## Как читать лог

**Вход в позицию:**
```
🔴 ВХОД SHORT 📉  POPCAT/USDT:USDT
   💵 Вход:       3 контракта = 1.73 USDT @ 0.05779
   💰 Профит (TP): +0.90%  →  0.05727  (+0.016 USDT)
   🛑 Убыток (SL): −0.59%  →  0.05813  (−0.010 USDT)
   ⚙️  Маржа 0.5779 USDT (5.7% депозита) · плечо 3x
   📌 📉 тренд вниз EMA20/EMA50 0.05789619<0.05798685 · RSI 42.3 в шорте 28-55
```

**Почему сделки нет** — строка по каждой паре на каждой свече:
```
⏭️  MEME/USDT:USDT — тренд вниз, а RSI 58.3 в зоне лонга 45-72 — ждём отбоя
⏭️  WIF/USDT:USDT — тренд вверх, но RSI 75.0 вне лонга 45-72
🚫 BTC/USDT:USDT — минимальный лот биржи — 1 контракт = 8.39 USDT, а сделка была бы 2 USDT
```

**Итог прохода** (раз в 15 секунд):
```
━━━━━━ ИТОГ ━━━━━━ пар 5/9 · просканировано 2 · нет сигнала 1 · уже в позиции 3 · входов 0 · позиции 3/5 · эквити 10.18 USDT
```

**Пульс** — когда сделок давно нет (раз в `HEARTBEAT_SECONDS`):
```
💓 Бот жив · сканирую 5 пар каждые 15с · позиции 3/5 · эквити 10.18 USDT · последний вход: MEW 12 мин назад
```

Значки:
- `🟢 ВХОД LONG` / `🔴 ВХОД SHORT` — позиция открыта
- `⏭️` — сигнала нет, дальше причина
- `🚫` — сигнал был, но риск-менеджер или биржа не дали открыть (с причиной)
- `🤖` — отклонил ИИ-фильтр
- `⏸️` — лимит позиций
- `🔄` — повтор того же сигнала на той же свече
- `⏱️` — пауза между входами
- `⚠️` — проблема с данными
- `🛑` — килл-ситч или файл `STOP`
- `💓` — пульс: бот жив, сделок нет
- `💰` — закрытие позиции

Бот **никогда не молчит**: у каждой пары на каждой свече есть строка —
либо вход, либо причина отсутствия входа.

## Стопы на реальных деньгах

На MEXC стоп-лосс и тейк-профит ставятся **отдельными plan-ордерами**
(единый `create_order` их параметры игнорирует). Бот ставит их сразу
после входа. Если стоп не поставился — в лог идёт строка
`🚨 позиция БЕЗ ЗАЩИТЫ!`, закрывайте такую позицию вручную.

### Особенности plan-ордеров MEXC, на которые ушло больше всего времени

Это не документация MEXC, а то, что выяснилось при живой проверке. Если
меняете работу с защитой — читайте сначала это.

**Поля ответа.** В `planorder/list/orders` у MEXC **не** `orderId` и
`quantity`, а `id` и `vol`. Полный набор, который реально приходит:

```
id, symbol, side, triggerPrice, vol, state, orderType,
executeCycle, positionMode, errorCode
```

**`side` в plan-ордере — это не сторона сделки, а код действия:**

| значение | смысл |
|---:|---|
| `2` | закрыть лонг (sell) |
| `4` | закрыть шорт (buy) |

`orderType: 5` — условный (план) ордер, `executeCycle: 2` — срабатывание
по цене, `triggerType: 1` — тейк-профит, `triggerType: 2` — стоп-лосс.

**`create_swap_order` теряет id.** Он делает `safe_dict(response, 'data')`,
а MEXC возвращает в `data` **строку**. Поэтому в `result['id']` id плана
нет. Бот выковыривает его обратным поиском — `find_plan_order()` ищет по
`symbol + side + triggerPrice` в списке планов. Номера ордеров
**не переиспользуются**: старый сработавший стоп и новый стоп на той же
цене не путаются.

**Отмена плана не работает.** `planorder/cancel` на живых данных отвечает
`code: 600 Parameter error` на любую комбинацию параметров (`orderId` строкой
и числом, плюс `symbol`, `side`, `openType`, `positionMode`).
`stoporder/cancel` и оба варианта `cancel_all` отвечают `code: 0`, но
заявка из списка не исчезает — то есть успех в ответе ничего не значит.

**`state: 2` не значит «активен».** Все 20 планов в аккаунте показывали
`state: 2`, включая явно отменённые. Проверить, жив ли стоп, на MEXC
программно **невозможно**. `planorder/list/orders` с параметром `{symbol}`
возвращает пустой список, без параметра — все 20, включая снятые.

Отсюда два практических следствия в коде:

1. **Недоверие к отправке.** После постановки защиты `_verify_protection()`
   перечитывает планы и пишет `🚨 … защита НЕ работает`, если стоп не
   найден. Молчаливое «отправилось» не считается успехом.
2. **Выход делает сам бот, а не биржа.** Раз планы нельзя надёжно проверить
   и снять, `manage_exits()` на каждом проходе сверяет текущую цену с
   записанными стопом и целью и закрывает позицию обычным ордером. Если
   стоп биржи сработал раньше, прилетает `Position is nonexistent` (код
   `2009`) — это обрабатывается как штатная ситуация.

**Осиротевшие планы.** Когда позиция закрывается, её стоп и тейк остаются
на бирже. Висящая заявка на закрытие может сработать позже и открыть
сделку, которой быть не должно. При старте бот зовёт
`sweep_orphan_plan_orders()` и снимает такие заявки. Так как отмена
ненадёжна, после её отказа в лог падает
`⚠️ Не удалось проверить висящие заявки` — тогда проверьте их в приложении
MEXC руками.

**Утилиты:**

- `python -X utf8 diag_state.py` — read-only дамп баланса, позиций и сырых планов
- `python -X utf8 cleanup_orphans.py` — список и отмена планов без позиции
  (`--all`, `--side buy|sell`)
- `python -X utf8 check_exits.py` — проверка, что позиции закрываются по
  цели и по стопу, а слоты освобождаются (пишет `exits_report.txt`)
- `python -X utf8 check_target.py` — во сколько процентов реально обходится
  цель по живым данным

## Аварийная остановка

- `Ctrl+C` в консоли — бот встаёт, **позиции и стопы остаются на бирже**
- файл `STOP` в папке бота — позиции закрываются и бот встаёт
- стопы риск-менеджера: `MAX_DRAWDOWN_PCT` от пика, `DAILY_LOSS_PCT` за день
